Token Ledger — Guide

What this is

Token Ledger estimates the token consumption and dollar cost of an LLM-based solution before you build it. You describe the architecture — which agents exist, what each one carries in its context, how they call each other — and it computes a per-request cost breakdown plus a daily/monthly projection under best, typical, and worst-case assumptions.

It is a sizing tool. Prompt sizes come either from text you paste (measured with a rough ~1-token-per-4-characters heuristic) or from token counts you type in directly, and the runtime behavior of a real system is assumption-driven — so treat every number as an order-of-magnitude estimate for budgeting and architecture comparison, not a bill.

Quick start

  1. Name the session (under the title) after your project — it becomes the export filename.
  2. Describe your first agent: pick provider & model, paste (or sketch) its system prompt, add its tools with rough schema text, and a representative user input. Prefer not to paste prompts? Flip on “Token counts only” and type sizes instead — see below.
  3. Set the per-turn sizes: average output tokens and average tool-result tokens per turn.
  4. Set loop iterations (best / typical / worst): how many model calls one invocation of this agent makes before it's done.
  5. Add subagents and wire them in the Calls section of whichever agent invokes them, with how many times per invocation.
  6. Set traffic (requests/day) and read the Estimate panel. Flip scenarios and the caching toggle to see the range.
  7. Export to save/share the model as JSON; Import restores it anywhere.

Core concepts

Agent

One LLM "role" in your system with its own model, system prompt, and tools. An agent with no incoming calls is an entry point (orange left border) and runs once per request. Everything else runs only as often as its callers invoke it.

Loop iterations — depth

How many turns a single invocation of the agent takes with itself: tool-call round-trips, self-verification passes, any back-and-forth before it finishes. Each turn re-sends the static prefix and the growing history, and produces one output.

Calls — width

Listed on the calling agent: which other agents it invokes and how many times per invocation. Each call spawns a fresh instance of the target — new context, no shared history with siblings. One specialist may be called by several different agents; its total invocations are the sum across all callers, multiplied up the chain:

invocations(agent) = Σ over incoming calls: invocations(caller) × calls-per-invocation entry points = 1 per request · 0 calls ⇒ 0 invocations ⇒ $0

Scenarios

Every iteration and call count has best / typical / worst values. Use them as sensitivity analysis: best = happy path (few turns, little fan-out), worst = retries, deep loops, maximum delegation. The spread between the three projections tells you how much your cost depends on runtime behavior you don't fully control.

Sharing without leaking prompts

Prompt text is never part of the calculation — it is only a convenience for deriving a token count (chars ÷ 4). The math consumes token counts and nothing else. So you can skip the text entirely with no effect on any number.

Turn on Token counts only in the top bar and every prompt field becomes a plain number input: system prompt size, each tool's schema size, and average user-input size. Switching it on also strips any prompt text already stored, so the saved model — and the JSON you export — carries sizes but no business logic. Estimates are identical before and after the switch.

Use it when you want to circulate a sizing model for review, attach it to a ticket, or hand it to procurement without shipping your system prompts along with it. The Export dialog tells you which mode the file is in before you copy it.

To get accurate counts without pasting text anywhere, run your real prompts through your provider's token-counting endpoint and type the results in.

The calculation, exactly

For each agent, in a given scenario, with n = loop iterations and inv = computed invocations per request:

Turn k of a loop sends: static prefix (system prompt + tool schemas) + user input (re-sent every turn) + history (all outputs and tool results of turns before k) — and produces one output. Tool results are input-only: turn k's result first appears in turn k+1's context. Summed over a whole request:

turns = inv × n static = staticTokens × turns user = userTokens × n × inv history = (outputTokens + toolResultTokens) × n(n−1)/2 × inv output = outputTokens × turns cost = user+history at input rate + static at cache rates (below) — or input rate if caching is off + output at output rate

Caching model

With caching on (and the agent marked cache-eligible), the static prefix is written to cache once per request — sibling invocations of the same agent reuse the warm entry — and every remaining turn reads it at the provider's discounted rate:

cacheWrite = staticTokens × min(inv, 1) cacheRead = static − cacheWrite

User input and history are billed at the full input rate — conservative, since some providers incrementally cache conversation history too. Static prefixes under ~1,024 tokens get a warning: most providers won't cache prefixes that small, so the discount may not materialize.

Anthropic and DeepSeek charge a premium on cache writes; OpenAI and Google don't (write = input price). The rates live in the Model prices table — all editable.

Real-life examples

1 · Customer-support chatbot (single agent, RAG)

One "Support Assistant" on Sonnet 5. System prompt with policies and persona ≈ 2,000 tokens; three tools (search_kb, get_order, escalate) ≈ 600 tokens of schemas; user question ≈ 120 tokens; answers ≈ 250 tokens/turn; a knowledge-base result ≈ 800 tokens/turn. Iterations 1 / 2 / 4 — best case answers directly, typical does one retrieval, worst does three.

Typical scenario, worked: 2 turns → static 2,600 written once, read once; user 240; history 1,050 (turn 2 carries turn 1's answer + retrieval); output 500. At Sonnet 5 rates that's ≈ $0.022/request → at 5,000 requests/day ≈ $110/day, ~$3.3k/month. The worst-case tab will show roughly 3× that — your retrieval hit-rate is the biggest cost lever.

2 · Code-review pipeline (orchestrator + subagents)

An Orchestrator (Opus 5) receives a pull request, splits it, and calls a Reviewer (Sonnet 5) once per changed file — calls 1 / 3 / 8. Each Reviewer runs a 2-turn loop (read diff → verify) with ~1,000-token tool results, and calls a Linter (Haiku 4.5) once.

The invocation math chains: Reviewer = 1 × 3 = 3 typical; Linter = 3 × 1 = 3. In the worst case (8 files) the Reviewer runs 8× and the Linter 8× — the Estimate panel shows how the cheap-per-call Reviewer dominates total cost through fan-out, which is the classic surprise in multi-agent budgets.

3 · Shared specialist (why calls live on the caller)

A research product has a Planner and a Builder, both entry-pointed from an Orchestrator, and both call the same "Explore" agent — Planner ×4 per run (scoping), Builder ×2 (verification). Explore's invocations sum across callers: 1×4 + 1×2 = 6 per request.

Because calls are recorded on the calling agent, you model this without duplicating Explore — and Explore's card shows "Called by Planner (×4 typical), Builder (×2 typical)" so the sharing stays visible. To evaluate "what if Builder trusted Planner's research?", set Builder→Explore to 0 in the best case and compare tabs.

Tips & limitations

  • Compare architectures, don't just price one. Duplicate via Export → edit → Import, or flip one agent's model/provider and watch the totals move.
  • Toggle caching off for a hard upper bound — useful when you can't guarantee cache hit rates (bursty traffic, prefixes that change per user).
  • History is often the sleeper cost. A 5k-token tool result carried through 6 more turns costs more than the system prompt. If worst-case history dominates, that's an argument for context editing or summarization in the real system.
  • Pasted text is sized at chars÷4. Real tokenizers differ by ±20–30%, more for code and non-English text. For precision, run representative text through your provider's token-counting API, then switch on Token counts only and enter the exact figures.
  • Prices go stale. Anthropic defaults were last verified 2026-07-24; OpenAI/Google/DeepSeek defaults are from July 2026. Verify against provider pricing pages before betting a budget on them — everything is editable under Model prices. Note Sonnet 5's introductory pricing ($2/$10) rises to $3/$15 on 2026-09-01.
  • Not modeled: thinking/reasoning token surcharges, batch-API discounts, long-context price tiers, per-image token costs, and rate-limit-driven retries. Pad worst case accordingly if these apply to you.
